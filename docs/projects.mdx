title: "Connecting projects"
description: "Add a Jig project to Jig UI and remove it again."
---

Jig UI shows the projects you connect on one page: each with its tasks counted and what waits for
you in it, a board of its tasks one click away, and each task's details from its card.

## Connect a project

**From the project's folder.** Run `npx @fapost/jig-ui` in the project — its root or any folder
inside it. Jig UI connects the project and opens its board, starting itself first if it is not
running. In a worktree it connects the clone's main checkout and says so. Run anywhere else, it
only starts. Running it again in a connected project changes nothing; it opens the board.

**From the page.** Paste the path of the project's **main checkout** — the folder you cloned — into the field at the
top of the page, above the projects, and choose **Connect**. A path inside the project works too; Jig UI connects the project's
root. `~/` stands for your home folder.

**By looking for them.** Choose **Find projects** to look for Jig projects in the folder typed in the
field, or in your home folder when the field is empty. Jig UI lists each one it finds that is not
connected yet, by its path, with **Connect**, and counts the ones already connected. It reads only
folder names — it runs nothing in a project before you connect it — goes 5 folders deep and through
at most 20 000 folders, and does not look inside a hidden folder or `node_modules`. It looks inside
a repository too, so a project kept inside another is found; a git submodule is not, so type its
path and choose **Connect**. On macOS it passes over Desktop, Documents, Downloads, Movies, Music and Pictures in your home folder,
because macOS asks before an app reads them, and says so: type one, `~/Documents` for example, and
choose **Find projects** to look there. It also passes over, without saying so, `Library` on macOS
and `AppData` on Windows, which hold apps' data.

The project needs [Jig 0.31.0 or later](/requirements). Each project gets a short id from its
folder name (`My Project` becomes `my-project`, a second `api` becomes `api-2`); the page names
it by that id.

A path is refused when it is:

- **not inside a git repository**, or does not exist;
- **a worktree.** A task started in a worktree keeps its records in the main checkout, which lists
  every task of the clone. Connect the main checkout instead (run from the worktree, the command
  does that for you);
- **a repository without Jig.** Run `jig init` in it first.

Connecting a project that is already connected changes nothing.

Jig UI reads a project by running the project's own Jig — `.ai/scripts/jig`, from the project's
files — when you connect it, after each change in it while the page is open, and once a minute.
Connect only projects whose Jig you would run yourself; that includes running
`npx @fapost/jig-ui` inside a project, which connects it.

## What the page shows

Along the top: `jig-ui://` for this page, and a dropdown that opens a project's board — type part of
its name to find it. Each project there shows how many things need you in it (a red `!` when it
cannot be read). The page is dark; the button at the right end switches it to light, and the browser
remembers the choice.

Below, the connected projects in a list, by name from A to Z, with a search and the same
counts. Choose one to see its card beside the list (above it on a narrow screen); the address keeps
the choice. Until you choose, the first project that needs you is shown, or else the first. When the
page opens, the list is there at once and each project fills in as Jig answers for it, `…` until
then, under a bar that counts the projects read: one slow project holds none of the others. The
card waits for every read before it picks a project for you, and **Upgrade all…** waits too. A
readable project's card shows:

- **Its live tasks counted** — `active`, `paused` and `ready` (finished tasks are not counted).
- **What needs you** — the same items `jig status` lists under "Needs you", most urgent first: a
  design waiting at its gate, a stopped autopilot run, a pull request waiting for review, a task to
  close. Each says what happened and what to do; a pull request comes with a link to it,
  knowledge waiting for your decision with **Decide on the page** ([Deciding knowledge](#deciding-knowledge)),
  and a merged task with **Close task** where its card in **Ready** could close it ([Closing a task](#closing-a-task)).
- **A note when pull request facts may be out of date.** Jig reads pull requests only during
  `jig housekeeping`; when its last run is old or the forge did not answer, a waiting pull request
  may be missing until it runs.
- **Housekeeping**, beside **Board**, runs `jig housekeeping` in the project — what Jig's session
  hook runs once a day: merged tasks' workspaces go to Jig's trash for 7 days, abandoned ones to the
  archive, the pull request facts are read again, and merged branches are deleted as far as the
  project's settings let Jig. The card shows Jig's report until you **Dismiss** it. Jig fetches
  first, so a dialog for your git credentials, such as the macOS keychain's, may ask you to allow
  it; the run waits for it up to two minutes.
- **The newer Jig on this machine**, after the project's own version, when the project runs an
  older Jig than the one installed here: *0.34.0 → 0.35.0 on this machine*, and **Upgrade…** to
  upgrade it from the page ([Upgrading a project's Jig](#upgrading-a-projects-jig)). Above the
  projects, a line counts how many need it. A project whose Jig says a newer release is out —
  *jig v0.38.0 is out* — gets **Upgrade…** too: it updates this machine's Jig first. So does every
  other project on an older Jig: a project hears of a new release only when its own
  `jig housekeeping` runs, and Jig UI takes the newest release any project has heard of.

The project's Jig says when it is behind, from Jig 0.34.0 on; a project on an older Jig shows only
its version, so compare it with `jig --version` yourself.

The page follows the projects while it is open — see [Staying current](#staying-current). A
project whose state is not readable shows why:

| Shown | Meaning |
| --- | --- |
| `Jig 0.31.0` | The project is connected and readable. |
| Answers in a form this Jig UI does not read | The project's Jig is newer than this Jig UI understands. Update Jig UI: `npx @fapost/jig-ui@latest`, or `jig-ui` if you [installed it without Node.js](/installation#without-nodejs). |
| Jig did not answer within 30 s | Each Jig run of a read has 30 seconds; a busy machine reading several projects at once can run past that. **Read again** reads it now; the next change in the project, or the read every minute, does too. |
| Jig could not be read | Jig refused the read — for example while an agent is writing to the project. The code in brackets is Jig's. **Read again** reads it now; the next change in the project, or the read every minute, does too. |
| Jig UI needs 0.31.0 or later | The project's Jig is older than Jig UI reads. Run `jig upgrade` in the project; it is shown as readable once the upgrade lands, without connecting it again. |
| The project directory is not there any more | The folder was moved or deleted. Disconnect it, then connect its new path. |
| There is no Jig in the project any more | Jig was removed from the project. |

## Upgrading a project's Jig

When Jig says a newer release is out and this machine's Jig is not on it yet, **Upgrade…** first
asks to update this machine's Jig: **Update Jig on this machine** runs `jig self-update`, which
moves the Jig installed here — the one every project upgrades from — to the newest release. It
changes no project. Then the card goes on as below. If it fails, the card says why: a framework
checkout with uncommitted changes, or a remote it cannot reach.

**Upgrade…** on a marked project asks Jig what the upgrade would do — `jig upgrade --dry-run`,
which changes nothing — and shows it on the card:

- what would stop it, when Jig would not start here: uncommitted changes, a started task's branch
  checked out in the project's main checkout, `jig verify` running. Deal with them and open it
  again;
- otherwise **Upgrade**, and the steps the release asks you to do by hand, if any;
- and a request to copy for your agent — *Upgrade Jig in &lt;project&gt;* — which upgrades the project
  and does those steps too. Jig UI runs no agent.

**Upgrade** runs `jig upgrade` in the project's main checkout, as you would in a terminal: Jig cuts
a branch, places its files, commits, and then goes as far as the project's `agent.git` lets it —
push, a pull request, a merge after CI. The card says *Upgrading…* meanwhile, in every browser tab and
after a reload. Until it ends Jig UI neither reads the project nor changes it: a change from the
board is refused, and the card offers no **⋯** menu. Then the card says what came of
it: merged, a pull request waiting for review with its link, pushed, committed, staged, nothing
to do, or why Jig stopped. It stays until you choose **Dismiss** or upgrade again, and until Jig
UI stops: it is not kept anywhere.

- With `agent.git: none` Jig stages the upgrade and leaves the main checkout on its branch; the
  card says how to commit it there.
- A push or a pull request is made by Jig with your git and `gh` credentials, as in a terminal;
  on macOS the Keychain may ask first.
- Stopping Jig UI while an upgrade runs stops the upgrade too — Ctrl+C in its terminal,
  `jig-ui stop`, or Jig UI running in the background alike — as Ctrl+C on `jig upgrade` in a
  terminal would. Run `jig upgrade` in the project to see where it stands.

### Upgrade all

**Upgrade all…** above the projects lists every project with an upgrade to make, and whether this
machine's Jig is updated first. Confirmed, it runs `jig self-update` when a project says a release
is out, then `jig upgrade` in each project in turn, one at a time, the order they were connected —
without the dry run each card shows. Each card says *Upgrading…* and then what its upgrade came
to, as above; the line above the projects names the project being upgraded and, at the end, which
were upgraded and which were left alone: up to date, or not readable just then. If `jig self-update`
fails, no project is upgraded and the line says why.

While Upgrade all or a self-update runs, no card offers **Upgrade…**; and **Upgrade all…** is
offered only while no project is being upgraded.

### An upgrade that waits for its pull request

Where the project's `agent.git` lets Jig open a pull request but not merge it, an upgrade ends on a
branch, and the project's main checkout stays on the Jig it had until the pull request is merged and
brought here. From Jig 0.39.0 in the project, the card says so — *The upgrade to 0.40.0 waits for
its pull request to be merged*, with the pull request's link — and offers **Check merge** instead of
**Upgrade…**, after a restart of Jig UI too: Jig remembers the pull request from its last
`jig housekeeping`.

**Check merge** runs `jig upgrade --land` in the project's main checkout. While the pull request is
open it says *Not merged yet* and changes nothing. Once merged, Jig checks the base branch out,
brings it up to origin's by fast-forward and deletes the upgrade's branch, and the card shows the
new Jig. Uncommitted changes, another branch checked out, or a base that cannot be fast-forwarded
stop it with Jig's reasons; Jig never stashes and never forces.

**Check all merges** above the projects does the same for every project with such an upgrade, one
at a time, and says which were brought up to date and which still wait. After **Upgrade all**, each
project is either upgraded or waits for its pull request, and its card offers **Check merge**.

A project on an older Jig shows the pull request as the run left it, until Jig UI stops; run
`jig upgrade` there once the pull request is merged.

## The board

The project's name or **Board** on a readable project's card, or the project in the dropdown at the top, shows its live tasks in five columns: Needs
you, In progress, Ready, Backlog, Paused — what waits for you first. Jig UI works the column out
from the task's state in Jig every time it reads it, and stores it nowhere; the first rule that
fits wins:

| Column | A task is here when |
| --- | --- |
| Paused | it is paused (`jig task pause`) |
| Backlog | it is filed but not started (`jig task start` not run yet) |
| Needs you | its design waits at its gate, or changed after approval, or its autopilot run stopped with a question |
| Ready | its work is done (`status ready`); the card says whether a pull request is open, its CI, or merged — on Jig's staging flow, why it waits at the staging branch ([Tasks on staging](#tasks-on-staging)) |
| In progress | anything else that is live |

A card shows the task's id, class and goal, its priority (`P0`, the most urgent, to `P5`) when it
has one, and what it waits for.

Finished tasks are not on the board. When the project has any, **N finished tasks** above the
board shows them in a list under it, the latest first: each one's id, *closed* or *abandoned*,
its goal, its pull request and the day it finished. Click it again to hide the list; it starts
hidden. Jig UI reads the list when you open it, and again on each change while it stays open. If
that read fails, the list says so and offers **Read again**; the board goes on as it was. The list holds what Jig still keeps: `jig housekeeping` moves a closed task's workspace to
trash once it sees the task's branch merged — for a task of an epic, once the epic reached the
default branch — and an abandoned one's after 14 days (`housekeeping.abandoned_ttl`); the task
leaves the list with it. From Jig 0.37.0 on, housekeeping archives the abandoned task instead and
keeps its notes; an archived task is shown nowhere on the board, and `jig task list --status
archived` lists them. A closed task that never had a branch, or whose branch housekeeping never
sees merged, stays. The history of finished work is the project's merged pull requests.

**Board / List** switches between the columns side by side and a list: the same columns as
groups of one-line rows, each group folding away; **Specs** shows the project's specs
([Specs](#specs)). The browser remembers the choice.

## Sorting and finding tasks

The bar above Board and List sorts and filters every column at once; it changes nothing in the
project.

- **Sort**: **Queue** — the order of the project's queue, the one agents follow — is the default.
  **Priority** puts P0 first and tasks with no priority last; **Class** puts T0 first and
  unclassified tasks last. Tasks that tie keep the queue's order.
- **Class** and **Priority** show only the tasks of the classes or priorities you tick; **None** is
  a task with no class, or no priority. Nothing ticked shows them all.
- **Find a task** keeps the tasks whose id or goal holds the text, in any case.

While a filter is on, the bar says how many of the project's tasks are shown, and **Clear** shows
them all again. The sort and the filters are part of the page's address: a reload keeps them, and a
link to the board with them opens it the same way.

## Filing a task

**New task** above the board opens a form: an id and a goal of one line. **File it** runs
`jig task new <id> --goal <goal>` in the project, and the task appears in **Backlog** once Jig
has written it. An id is letters, digits, `.`, `_` and `-`, not starting with `.` or `-`. An id the
project already has is refused — a finished task's too, though only the list of finished tasks
shows it.

The rest of a task — its class, domains, a longer description — is set in the terminal, or by
the agent that starts it.

## Ordering the work

Inside a column the tasks stand in the order of the project's queue in Jig (`jig queue`): the
queued tasks first, then the ones not queued yet, in Jig's order. Agents see the same queue in
`jig status` and `jig context`.

- **Drag a card** up or down within its column, on the board or in the list. Jig UI runs
  `jig queue move` in the project; the card moves once Jig has written it, not before, and says
  *sending to Jig…* meanwhile. A line marks where it will land; where there is none, Jig's order cannot
  put it there — for example inside the run of tasks on another epic.
- **The ⋯ menu** on a card or row does the same without a mouse: **To top**, **Up**, **Down**,
  **To bottom**, and **Priority** from P0 to P5, or none (`jig queue set --priority`).

On a board sorted by **Priority** or **Class** a card is not dragged within its column and its
menu has no **To top**, **Up**, **Down** or **To bottom**: its place there is not the queue's.
Sort by **Queue** to order the work. A filter keeps both: a card moves among the cards shown,
and **To top** or **To bottom** past the hidden ones too.

A queue starts empty: a task joins it the first time it is moved, so the first card you drag
goes to the top of the queue or right after the last queued task above it.

If anything was written in the project between the moment the board was read and your change —
an agent working, a `jig` command in a terminal — Jig refuses the change, so nothing written
meanwhile is overwritten. The page reads the board again and shows the conflict:

- the line above the board says what became of your card — *beta is now in Ready*, *beta moved in
  Backlog*, *beta is no longer on the board* — and how many other cards changed;
- each card that changed while you acted says *Changed while you acted* (*changed* in the list):
  new, in another column, moved within its own, or with other facts, such as its priority. The
  marks show what changed up to Jig's refusal; the board itself keeps following the project.

Jig counts every write in the project, so the line may say *nothing on the board changed*: an agent
wrote elsewhere, a document or a stage. Make the change again on the board as it is now;
**dismiss**, or your next change, clears the marks.

## Pausing a task

**Drag a card onto Paused**, or choose **Request pause** in its ⋯ menu, to ask the task to pause.
Jig UI runs `jig queue request task:<id> pause`; the task is not paused at once. An agent working
on it pauses at its next stage boundary, and a task nobody is working on pauses when its next
stage begins. Until then the card stays in its column and says *Pause requested 12 min ago*, with
**cancel** to take the request back (`jig queue cancel`, also in the ⋯ menu). Paused is offered
only where Jig offers the request: not for a task already paused, and not twice.

## Resuming a task

**Drag a paused card out of Paused**, or choose **Resume** in its ⋯ menu, to resume it. (A task
parked at a staging branch is taken back the same way: [Tasks on staging](#tasks-on-staging).) Jig UI
runs `jig task resume <id>` in the project's main checkout, with the revision of the board you saw,
and the card moves to the column the task is in once resumed: that column is the only one the
drop is offered on.

A task paused with `jig task pause --stash` kept its changes in a stash, and resuming applies the
stash again — as `jig task resume` in a terminal does, in the project's main checkout. Jig does
that only when the checkout is on the task's branch; otherwise the line above the board says to run
`jig task resume <id>` there. When the stash does not apply cleanly, the task stays paused and the
line says to resolve the conflicts in the checkout first. A pause Jig UI asked for never stashes.

Resuming from the board needs Jig 0.35.0 or later in the project. With an older Jig the card says
how to resume it — run `jig task resume <id>` in the project — and **Resume** is off.

A drop on any other column does nothing.

## Closing a task

A card in **Ready** whose task can be closed carries a **✕** beside its ⋯ menu. Press it,
then **Close task** in the question below it, to close the task as done: Jig UI runs
`jig task set <id> status consolidated` — the command Jig's own `close` action names — in the
project, checked against the board you saw: from Jig 0.40.0 Jig itself refuses the close when
anything was written there since; with an older Jig, Jig UI reads the project just before. The card
leaves the board and shows in the list of finished tasks.

The same close is on a project's card on the Projects page: Jig's item *Merged: the task can be
closed* carries **Close task** for a task the board would offer to close. Press it, then **Close task**
in the question below it; the close is checked against the project as the card shows it, and a refusal
stays on the card in Jig's words until you **Dismiss** it.

Jig decides whether the task may close, not Jig UI. It closes a task only once its knowledge
decision is recorded and its pull request has merged, and it asks the forge about the merge as it
closes. When it refuses — the pull request is still open, say — the line above the board says why
in Jig's words, and the card stays.

The ✕ is shown on a ready task whose knowledge decision is recorded and whose pull request is not
known to have closed unmerged. What Jig knows of pull requests between commands comes from
`jig housekeeping`; in a project where it has not run since the merge, Jig itself does not offer
to close the task yet, and the ✕ is there anyway, since closing asks the forge. A task without a
recorded knowledge decision has no ✕, and its item no **Close task**: record it first (the
`jig-consolidate` skill). Closing cannot be undone from the page.

## Tasks on staging

A project on Jig's staging flow (`git.flow: staging`, from Jig 0.45.0) ships each task's pull request
into a staging branch first. The task waits there, *parked*, while it is tested, and reaches the main
branch through a second pull request once someone says "prepare for prod"
([Test on staging first](https://jig.fapost.in/staging-flow)). A parked task stays in **Ready**, and
its card says why it waits instead of what its pull request did:

| The card says | The task |
| --- | --- |
| Pull request into staging waits for review | its pull request into the staging branch is open and waits for a review |
| Pull request into staging — yours to land | the same, and landing it is yours: your `agent.git` is below `merge`, so merge it on the forge or run `jig task land <id>` |
| On staging, waits for prepare for prod | its work is on the staging branch; once it passed its test there, tell your agent "prepare for prod" |
| Fix not on staging yet | you took it back for a fix, and the fix has commits the staging branch does not have yet |
| Promotion open, CI green | its promotion, the pull request into the main branch, is open; the note follows its state and CI |
| On staging | its work is on the staging branch, it does not wait there, and it has no promotion yet |

**Take back for a fix** in a parked card's ⋯ menu, or a drag of the card onto **In progress**, runs
`jig task resume <id>` with the revision of the board you saw: the task is active again, and once it
ships again its fix lands on the staging branch as the first change did. Landing and "prepare for
prod" have no button: Jig answers neither as data the page can read, so they stay with your agent,
or your CI.

A task on the staging flow has no ✕ until its work is in the main branch. Landing on staging does not
finish a task, yet Jig 0.45.0 offers to close one as soon as its pull request into staging merged.
On this flow Jig UI offers the close only once `jig housekeeping` saw the work in the main branch: the
task's item *Merged: the task can be closed*. **Housekeeping** on the project's card runs it.

## Specs

**Specs** — the third choice beside Board and List — shows the project's specs as Jig's
`jig spec list` reports them, one at a time: with more than one, a tab for each, in the order
below, chooses which, and the page's address keeps the choice. A spec shows its title, how many
roadmap items are done out of all of them, and its fog. An epic shows its branch, whether it is open or finished, and whether its
roadmap was read from the remote branch as it was at the last fetch, or the branch is nowhere;
the version level its release raises is shown when the roadmap records one.

Its phases stand in a row of steps, each with how many of its items are done, or ✓ once all of
them are; items before the first phase heading have a step of their own. The page opens on the
first phase with an item not done, and a click on a step shows another. The chosen phase's items
stand in three lanes, each in the roadmap's order: **To file** — not done and naming no task, fog
included, in italics —, **In work** — naming a task, with the column the board shows it in, or
*filed* when the board does not show it — and **Done**. Each item is a card: its words up to the
first dash, and under them the task it names and its dependencies (`after: …`); a click on the card
shows the rest of its words. An item that names a live task links to the task's details. A spec
missing `spec.md` or `roadmap.md` says so. The specs follow the project like the board does.

### Asking your agent

The page plans nothing in a spec itself: a spec with work for your agent offers the request to
copy. For the first phase with an item that has no task, it is *File the tasks for phase 3 of spec
shop in acme*; while the spec has fog, *Continue spec shop in acme: lift its fog items*. Your agent
takes them with Jig's `jig-idea` skill.

### Ordering the epics

The specs with an open epic come first, in the order of the project's queue — the order in which
`jig queue next` takes their tasks — then the specs with none. An epic's ⋯ menu moves it **Up** or
**Down** past the epic next to it, or **To top** or **To bottom** of the whole queue, ahead of or
after the tasks that belong to no epic too; it also sets the epic's priority, from P0 to P5, shown
beside its title and on its tab. Jig UI runs `jig queue move` and `jig queue set` with the revision of the specs
you saw, so a change made in the project meanwhile is refused and the specs are read again. An epic
not moved or prioritised yet is not in the queue; it follows the ones that are, in Jig's order.
Setting its priority puts it in the queue too, at the bottom.

### Editing a roadmap

With Jig 0.40.0 or later in the project, a spec's roadmap is edited on the Specs view:

- **Add item**, under the lanes of a numbered phase, adds a line at the end of that phase. Items
  before the first phase heading have none.
- An item's ⋯ menu moves it **Up** or **Down** past the next card in its lane — the items of the
  other lanes keep their places — or **To Phase N**, to the end of another phase.
- **File task…**, on an item not done that names no task, fog included, files the item's task and
  names it on the item: give the task's id, and its goal, which starts as the item's own words.
  A fog item's goal starts without its `fog:`. The task goes to
  Backlog. The id of a task the board shows names that task instead, with no goal.

Jig UI runs Jig's `jig spec item add`, `move` or `file` with the revision of the specs you saw, as
for the epics. Jig commits each edit on the
spec's branch, `spec/<spec-id>` — or the open epic — in a tree of its own, never in your checkout,
and takes it as far as `agent.git` lets it: committed, pushed, a pull request. The line above the
specs after an edit is Jig's note on the next step, such as *agent.git is commit: pushing
spec/shop is yours*.

While edits wait on that branch, the spec says so — with a link to the pull request, or *pushed,
no pull request yet*, or *committed in this clone, not pushed* — and shows the roadmap as it is on
the branch, the one the next edit changes. Each item an edit added, moved to another phase or
filed there is marked **waiting**. Once the pull request is merged and the project fetched, the
roadmap is the default branch's again.

Jig refuses edits when:

- `agent.git` is `none` (Jig's default) in your clone: Jig commits nothing. Choose a level in the
  project's **Settings**. Filing a new task files no task then.
- the spec's branch is checked out in a checkout of yours, as `jig spec new` and `jig spec resume`
  leave it: switch that checkout to another branch first.
- the project changed since you saw the specs: they are read again; try again on them.
- an earlier edit of the spec still waits where this one cannot follow (Jig 0.41.0): an epic was
  opened or finished since, or edits that never reached the remote sit above a pull request closed
  unmerged, or above edits the remote no longer has. Jig's line says what to do.
- the id given to a new task is a finished task's: choose another id. When the item already names a
  task on the spec's branch, for example one filed in another clone, Jig's line says so.

With Jig 0.41.0 or later, filing a new task is one Jig command, `jig spec item file --new`, with
the revision of the specs you saw, as for every other edit: a change made in the project since then
refuses it, and the specs are read again. When Jig refuses it, no task is filed.

On Jig 0.40.0 it is two Jig commands: `jig task new`, which carries no revision, then
`jig spec item file` with the revision Jig has right after it. So a change made in the project
since you saw the specs does not refuse it: the item is found by Jig's own handle for it, and Jig
refuses an item that names a task already. If Jig files the task but then refuses to name it on
the item, the dialog says so and why; once that is resolved, **File task…** again with the same
id names it, without filing a second task.

Rewording, checking off or removing an item is not here: ask your agent.

## Deciding knowledge

**Knowledge** — the fourth choice beside Board, List and Specs — shows what waits for your decision
in the project's knowledge: documents proposed and not agreed to yet, and the files linked by
approved documents that changed since they were approved. It needs Jig 0.40.0 or later in the
project; on an older Jig it says which Jig the project runs. On the projects page, a card's items
about knowledge or linked files waiting for your decision link here with **Decide on the page**.

A proposal shows its id, type, summary and file, the paths and domains whose tasks it would make
agents read it for, and for a document that links a file of the project, that file and its size —
or that it is missing. **Accept** or **Reject** decides it.

**Document** opens its text, with the fields shown above it left out, and for a document that links a
file, that file as it is now. A Markdown file is shown formatted; any other file as it is. This needs
Jig 0.41.0 in the project; on Jig 0.40.0 each proposal names the file to read before you decide.

A changed file shows **Diff since approved**, Jig's diff of it since it was approved. **Keep**
approves the file as it is now. **Drop** ends the link: agents are no longer sent to the file. A file
with no approved text kept to compare with says so: read it whole before you keep it. A file that is
gone has only **Drop**, or move the link in the project with your agent (`jig-accept`). Drop needs
Jig 0.41.0; on Jig 0.40.0 a gone file has no button.

Jig UI runs `jig knowledge accept`, `reject` or `reviewed` with the revision of the knowledge you
saw. Jig commits each decision on the branch `knowledge/decisions` in a tree of its own, never in
your checkout, and takes it as far as `agent.git` lets it, as for [roadmap edits](#editing-a-roadmap).
A decided document stays in the list, marked *Accepted, waiting*, *Rejected, waiting*, *Kept,
waiting* or *Dropped, waiting*, until that branch's pull request is merged; a line above the lists
says where the decisions wait.

On Jig 0.41.0, a document Jig cannot decide yet says why above its buttons: it is committed only in
your clone — push it first, then decide —, or it reached the default branch after the decisions
waiting were started — decide it once they have landed. Jig fetches before it decides, so a decision
sent after the push goes through; one sent too early is refused with Jig's reason.

Jig refuses a decision when:

- `agent.git` is `none` (Jig's default) in your clone: choose a level in the project's **Settings**.
- the document is proposed in a commit not on origin's default branch yet — `knowledge/decisions`
  starts from there: push that commit, or let the decisions waiting on the branch land first.
- `knowledge/decisions` is checked out in a checkout of yours: switch it to another branch first.
- decisions committed on `knowledge/decisions` in your clone never reached origin, above ones origin
  no longer has: Jig says how to move them to a branch of your own.
- the project changed since you saw the knowledge: it is read again; decide again on it.

## Task details

A click on a card opens its details inside the card; in the list, the row's details appear in a
pane on the right. **copy id** beside them copies the task's id. **Open full details** shows them on a
page of their own, with an address you can keep, and with what Jig offers. The details are:

- **Its place in the queue** — its priority, its place among the live tasks and open epics of its
  level (*2nd of 5 at the top*, *1st of 3 in epic booking*, or *not queued*), and what it waits for,
  with the reason given to `jig queue depend`: its own dependencies, then its epic's, as they were
  declared, met or not.
- **Where it stands** — its column, status, class, branch and the branch it lands on, how many
  files are uncommitted in its worktree, whether its knowledge decision is recorded, and when it
  was filed and last changed.
- **Its design gate** (T3 and T4) — waiting for approval, changed after approval, or approved.
- **Its autopilot run** — the stage it entered last and, when it stopped, the question it stopped
  on.
- **Its pull request** — open, merged or closed, its CI, and a link, as Jig's last
  `jig housekeeping` heard it.
- **What needs you** about it, and the housekeeping flags that still stand for it.
- **What Jig offers now**, on the full page only — each step Jig would accept on the task as it is (approve the design,
  answer the autopilot, pause, ship, close…) with the command to run in the project and a **copy**
  button. Jig UI runs none of them; the page follows the change once you do.

- **Its documents**, on the full page only — the ones its workspace holds (task, discovery, design,
  plan, review…), each with when it was last written and its size. A click opens one below its name,
  rendered from its Markdown; an agent rewriting it is followed as the board is. A document is shown
  as its authors wrote it, paths included. Anything in it that could run in the page — a script, an
  event handler, a form — is taken out. Needs Jig 0.39.0 or later in the project.

A finished task has no details page; its link says so.

## Staying current

While the page is open, Jig UI watches each connected project's `.ai/` folder. When an agent or
a person changes a task — through Jig, by editing a file, or with git (a pull, a checkout) — the
workspace and the board show it within about two seconds, without a reload. Every minute each
project is also read again, for a change the system did not report.

A read that fails while an agent is in the middle of writing does not blank the page: the last
good read stays until the next one. A project that keeps failing shows why, as in the table above.

Watching stops when the last page closes; watching writes nothing in the project. If the page says its
session has ended, the browser was closed since the page was opened, the token was reset, or Jig UI
now runs on another port: run
`jig-ui open`, or `npx @fapost/jig-ui`, to reopen it. A restart of Jig UI does not end it.

## Settings

**Settings…**, in the **⋯** menu on a project's card, shows the project's Jig settings as
`jig config keys` lists them, in two parts. Each key says where its value comes from.

- **Yours, in this clone** — the keys you can set for this clone alone, in its gitignored
  `.ai/config.local.yaml`; a value set there wins over the project's. Change one here: a box for
  yes or no, a list for a fixed set of values, a field for the rest (**Save**, or Enter). Jig UI
  runs `jig config set <key> <value> --local` in the project. **Unset** runs
  `jig config unset <key> --local`, and the key falls back to the project's value or Jig's default.
- **The project's, shared through git** — the keys only `.ai/config.yaml` holds. They are shown,
  not changed: change that file and commit it, so everyone on the project gets the change.

Jig checks each change itself, against the settings you saw. A value it refuses is not written, and
the dialog says why in Jig's words. A setting changed since the dialog read them — in a terminal, by
an agent — is not overwritten: the dialog reads them again and says so.

The Telegram token is never shown, only whether it is set. **Clear** removes it; set it with
`jig notify setup` in a terminal in the project — Jig never takes it on a command line.

Needs Jig 0.40.0 or later in the project.

## Disconnect a project

**Disconnect**, in the **⋯** menu on the project's card, removes the project from Jig UI. Nothing in the project changes: Jig UI never
writes a file in a project.

## Where the list is kept

The list of connected projects is `projects.json` in Jig UI's config folder —
`~/.config/jig-ui/` (or `$XDG_CONFIG_HOME/jig-ui/`) on Linux and macOS, `%APPDATA%\jig-ui\` on
Windows. It survives a reinstall. If the file is damaged, Jig UI says so and leaves it as it is,
so you can fix or remove it.
